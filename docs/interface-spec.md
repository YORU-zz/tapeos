# TapeOS インターフェース仕様

本書は、TapeOS において上層プログラムがモニタ／シェルに依存してよい
契約（インターフェース仕様）の正本です。新規に発明したものではなく、
開発過程で蓄積された設計資料・各部の報告・ソース中のコメントから、
既存の契約を集約したものです。矛盾する場合は一次資料（ソース）が
優先します。

本書は開発側の正本の公開写しです。機械チェック可能な項目は
`tools/contract-check.sh`（基準値 `tools/contract-manifest.txt`）が
検証します。対応関係は §7 にまとめています。

著者について：本プロジェクトの設計・方針・検証は asa2yoru が担当し、
実装とドキュメントの記述は Muse（AI）が担当しています（共著）。
プロジェクト全体のライセンスは MIT です（LICENSE を参照して
ください）。

典拠区分:

- 原作本文に根拠がある項目
- 再現側の設計・実装決定
- 実機または互換実装（互換 IPL 等）の事実
- 資料に定めが無い、または未決のまま残す項目（§8 にも集約）

## 1. IOCS コールテーブル

### 1.1 配置と呼出し形式

- 作中では MZ-80B の IOCS エントリ（28 個）を解読し（第 5 話）、
X1 上に MZ-80B 互換コールテーブルを実装して共通モニタ化した（第 18–19 話）。
本再現も 28 エントリの固定ジャンプテーブルという形を踏襲する。
- エントリの具体的な並び・名前・引数の割当ては再現側の決定である
（原作の MZ-80B IOCS の正確なエントリ一覧は作中に示されていない）。
- テーブルは 28 エントリ × 3 バイトの `JP` 命令。呼出しアドレスは
`IOCS_BASE + 3 * 番号`、通常の `CALL` で呼ぶ。
実体は各機種の `iocs_template` を起動時に `LDIR` で `IOCS_BASE` へ
28×3 バイト複写して構築する。
- **X1 系 2 ビルド（通常版／4800 版）は 31 エントリに拡張した**
（契約の「追加」であり、既存 28 エントリの
番号・アドレス・規約は不変）。追加分は 28 SIN／29 SOUT／30 SPOLL
（シリアル、§2.6 の RS-232C ボードが実体）で、X1 系のみに存在する。
MZ 両機／PC-8801 は 28 エントリのまま。X1 系の複写は 31×3 バイト。
- 配置アドレス（機種定数 `IOCS_BASE`）:

| 機種 | IOCS_BASE | 理由 |
|---|---|---|
| X1 | 0xE400 | — |
| MZ-80B | 0xC400 | TVRAM を 0xD000 に置くと GVRAM が 0xE000–0xFFFF に現れ 0xE400 を RAM として使えない |
| MZ-80K | 0xC400 | 0xE000 台は I/O 空間のため不可。80B と同アドレスに揃えた |
| PC-8801 | 0xE400 | — |

- 番号と呼出し規約は共通層（`src/common.inc`）で統一され、
ジャンプ先の実体は機種別。`common.inc` にシンボル定義があるのは
27 エントリ（0–19, 21–27）で、17–19 と 27 は X1 拡張 IOCS
（第 31 話、§2.5）の MINIT／MDIR／MSTORE／MFREE として定義される。
20–23 の名前は機種によって異なる（§1.3 の表を参照）。
28–30 は X1 系のみの追加エントリで、`common.inc` でも X1 限定で
定義される（他機種で誤って参照するとアセンブルエラーになる）。

### 1.2 共通レジスタ規約

- 原則として **BC / DE / HL は保存される**。引数・戻り値はすべて
レジスタ経由（HL が指すバッファ／文字列／情報ブロック自体はメモリ経由）。
- 明示された例外は 3 件のみ:
- 3 PRTMSG: HL は文字列の終端子の直後まで進む。
- 20 DELAY: HL は破壊される。
- 26 RINIT: HL は戻り値（確定ブロック数）。
- **未実装エントリはキャリセットで戻る**（スタブ実体は `SCF / RET`）。
- メディア／テープ系エントリはキャリをエラー表示に使う（§1.3）。
ただし PC-8801 の FD 層は §8 の例外がある。
- AF／フラグの保存（上記キャリ意味論を除く）と、
**全エントリのスタック消費量**には数値規定が無い。実装は PUSH/POP で
レジスタ保存を担保するが、消費バイト数は契約に含めない（§8）。

### 1.4 RST 28H ラッパー（MZ-80B／MZ-80K のみ）

- MZ-80B 側で RST 28H をフックして IOCS コールへ変換する
ラッパーは第 19 話に典拠がある。
- 呼出しは `RST 28H`、**C レジスタ = 機能番号（0–27、IOCS 番号
そのもの）**。機能番号を C に置くのは「A を CONOUT/HEXOUT の引数として
空けるため」の再現側決定（原作は置き場所まで特定していない）。
- ディスパッチ自体は全レジスタ保存（フラグのみ非保存）。各エントリの
引数／戻り値はテーブル直接呼出しと同じ。範囲外番号は即リターン。
MZ-80K ではラッパーは自作 IPL.ROM 内にあり、OS ロード前はテーブルが
ROM 内スタブ（キャリセット）への JP で先行充填される。
- X1／PC-8801 に RST 28H 接口は無い。

### 1.5 テーブル経由でない接口

- **シェルの G／J コマンドによる起動**: シェルは戻りアドレス
`shell_loop` をスタックに積んで対象へ跳ぶ。**対象は `RET` でシェルへ
戻る**のが契約。引数レジスタ等の取り決めは。
- **ファイル層は IOCS に無い**: TOSD の名前付きファイル操作（§3）は
シェルと各ツールがブロックエントリ（15/16, 24–26）の上に各自実装した
層であり、IOCS の接口ではない（§8）。
- **常駐デバッグスタブ（X1 のみ、テーブル外）**: シェルコマンド `X` で起動。ブレークポイントは RST 30H
（0xF7）へのソフトウェアパッチ方式（ワンショット）、ベクタは
0x0030／0x0038／0x0066 にブート時設置。ホストとのメールボックスは
0xEA00–（MB_FLAG 0xEA00、MB_STATE 0xEA01、MB_OLEN 0xEA02、
署名 "DBST" 0xEA04、MB_LINE 0xEA10（48B）、MB_OUT 0xEA40（256B））。
スタブスタック 0xEB40–0xEC00、レジスタ退避域 0xEC10。
転送層の継ぎ目はメールボックス読み書きに局所化されており、実機では
第 46 話式の 6 ビットパラレル転送ドライバに差し替える箇所である
。

## 2. メモリマップ保証

### 2.1 機種別基本配置

| 項目 | X1 | MZ-80B | MZ-80K | PC-8801 |
|---|---|---|---|---|
| 本体ロード先 LOADADDR | 0x2000 | 0x0000 | 0x1000 | 0xC100 |
| スタック頂点 STACKTOP | 0xE000 | 0xC000 | 0xC000 | 0xE000 |
| IOCS テーブル | 0xE400 | 0xC400 | 0xC400 | 0xE400 |
| 起動署名 SIGADDR | 0xE100 | 0x9200 | 0x9200 | 0xE100 |
| ワークページ | 0xE000 台 | 0xC000 台 | 0xC000 台 | 0xE100–0xE8FF |
| テキスト VRAM | （GRAM 方式） | 0xD000 | 0xD000 | 0xF000 へ移設（窓 3,000B） |

- ロード形態: X1 は互換 IPL が FDD から 0x2000 へロード（IPL はブート後
切り離される）。MZ-80B は MZT ダイレクトロードで 0x0000 常駐。
MZ-80K は ROM（0x0000–0x0FFF、自作 IPL、常時マップ）がベクタと
RST 28H を持ち、本体はテープから 0x1000 へロード。PC-8801 は疑似 BIOS
が IPL セクタを 0xC000 へ読み、本体はその直後 0xC100。
- MZ-80B のモニタ本体は 0x189F までで終わる（RAMDISK seg1 の 0x2000
開始が安全な根拠）。MZ-80K の本体ゾーンは 0x1000–0x2FFF。
- X1 の常駐デバッグスタブ用空き領域は 0xE900–0xFFFF（§1.5）。

### 2.2 ワークエリア

全機種で同型オフセットに配置される（X1／PC-8801 は E ページ、
MZ 両機は C ページ。PC-8801 の LASTCMD とキー記録は +0x10 ずれる）。

| ワーク | X1 | MZ-80B／80K | PC-8801 | 用途 |
|---|---|---|---|---|
| LASTCMD | 0xE110 | 0xC110 | 0xE120 | 最終コマンド行（32B） |
| KEYLOGN／KEYLOG | 0xE13F／0xE140 | 0xC13F／0xC140 | 0xE15F／0xE160 | 受理キーコード記録 |
| LINEBUF | 0xE300 | 0xC300 | 0xE300 | シェル行入力バッファ |
| KBBUF（16B リング） | 0xE340 | 0xC340 | 0xE340 | KBHEAD +0x10／KBTAIL +0x11／KBPREV +0x12 |
| NAMEBUF | 0xE358 | 0xC358 | 0xE358 | FD ファイル名（10 文字、空白詰め） |
| TNAMEBUF | 0xE368 | 0xC368 | 0xE368 | テーププログラム名（13 文字、空白詰め） |
| SUBBUF／TAPEBUF | 0xE380 | 0xC380 | 0xE380 | E コマンド入力／テープ情報ブロック（共用） |
| DIRBUF | 0xE500 | 0xC500 | 0xE500 | TOSD ディレクトリセクタ（256B） |
| KFSIG | 0xE6D0 | 0xC6D0 | 0xE6D0 | 漢字成功マーカー "MSK8-OK" |

- MZ 両機のみのテープワーク: TPHDR 0xC900（128B MZ ヘッダ）、
TPHDR2 0xCA00（ヘッダ copy 2）、TPWORK 群 0xC980–（チェックサム、
ポインタ、較正値 TP_BTHR 等）。
- IDXBUF の MZ 配置（0xCB00）は、テープワークの実割当てが 0xCA7F
までであることから、その直上に予約したものである。X1／PC-8801 の
0xE700 はワークページ内の未割当て域に新規予約する。
- **位置づけ**: これらはモニタ内部変数と検証ハーネス用証跡領域であり、
アドレスは `machine_*.inc` の定数として固定されるが、**上層プログラム
向けの接口としては保証しない**（§8）。例外的に PC88 の SETATR は
`cur_attr` を接口として操作する。

### 2.3 プログラム領域 0x4000

- TOSD プログラム（EDAS／NEWASM／SCED）は **0x4000 にロードされる**
通常プログラムとして作る（各ソースの `org 04000h`）。シェルの `R` で
読み、`G 4000` で起動する。
- 0x4000 という値自体の選定理由は資料に。作中典拠も無い。
分離の必然性のみ明記されている: FD システム領域の制約でシェルは
7,936 バイト上限（§6）であり、エディタ＋アセンブラは物理的に
入らないため別ファイル化した。
- NEWASM／SCED の配置枠は **0x4000–0x6800 ＝ 10,240 バイト**
（自前 DIRBUF 0x6800 の手前まで）。
- EDAS ゾーンとして 0x4000–0x7FFF が予約扱い（RAMDISK 裏付けの
除外根拠として各機種がこのゾーンを明示する）。EDAS 内部マップ:
EDIRBUF 0x6400（ディレクトリセクタ自前コピー 256B）、シンボル表
0x6600–0x6DFF（128 件×16B）、ソーステキスト 0x7000–0x7FFF（4KB、
各行＝長さバイト＋文字、終端 0xFF）、出力／ステージング 0x8000–。
- アセンブル出力レンジガード [OUTMIN, OUTMAX): OUTMIN 0x8000 共通、
**OUTMAX: X1＝0xE000／MZ＝0xD000（テキスト VRAM 手前）／PC-8801＝0xC000
（OS 本体手前）**。

### 2.4 RAMDISK／EMM 配置

- 論理仕様は全機種共通: **256 バイトブロック、最大 256 ブロック
＝64KB**（第 19 話）、動的に拡張／縮小（再構成）可能（第 47 話）。
RINIT は要求を min(256, 機種 RDCAP) にクランプし確定値を返す。
- X1: EMM 上に置き、メインメモリを消費しない。
- EMM ポート: 0x0D00＝アドレス下位（bits 0–7）、0x0D01＝中位（8–15）、
0x0D02＝上位（16–23）、0x0D03＝データ（自動インクリメント）。
アドレスレジスタは L→M→H の順に書く。
- EMM デバイス自体は 1MB 裏付け（xmil コア側パッチ、リセットでゼロ化）。
TapeOS は作中仕様どおり 64KB＝256 ブロックで運用上限をかける。
- RAMDISK 領域: EMM バイトアドレス＝ブロック番号×256、すなわち
0x00000–0x0FFFF（ブロック 0＝ディレクトリ、1–＝データ）。
- SCED バッファ（RAMDISK と非重複）: バッファ 1＝EMM 0x10000–0x15FFF
（24KB）、バッファ 2＝0x16000–0x1BFFF（24KB）。作中の「GRAM を
24KB で区切る暫定 2 ファイル」を EMM へ読み替えたもの（X1 の GRAM
はセルアドレス方式で線形ストアに使えないため）。
- EMM 0x1C000 以降の割当ては。
- MZ-80B／MZ-80K／PC-8801: 実 RAM 裏付け（EMM なし）。2 セグメント構成:

| 機種 | セグメント 1 | セグメント 2 | RDCAP |
|---|---|---|---|
| MZ-80B | 0x2000–0x3FFF（32 ブロック） | 0x8000–（64 ブロック） | 96（24KB） |
| MZ-80K | 0x3000–0x3FFF（16 ブロック） | 0x8000–（64 ブロック） | 80（20KB） |
| PC-8801 | 0x0000–0x3FFF（64 ブロック） | 0xFC00–（4 ブロック） | 68（17KB） |

除外根拠は EDAS ゾーン（0x4000–0x7FFF）、ワークページ、VRAM、
I/O 領域。本体 RAM 内で連続確保できるのは上表のみであり、作中の
64KB は EMM という別メモリの裏付けあっての値として、クランプ結果で
正直に報告される。

### 2.5 メインメモリプール（拡張 IOCS、X1 のみ）

第 31 話の「メインメモリ管理の RAMDISK 共通化」を、再現側で初めて
導入する FAT 方式のブロック管理として X1 クラシックビルドのみに
実装したもの（`EXTIOCS`、§8-16 に制約と作中との差異）。

- **プール**: メインメモリ **0x9000–0xCFFF、256 バイトブロック、
  最大 64 ブロック**。EDAS ゾーン（0x4000–0x7FFF）とワークページ
  （0xE000 台）の間の連続空き領域。MINIT の要求は 64 にクランプ
  され、確定値が返る。プールは RAM 上のみに存在し、リセットで
  失われる（永続化されない）。
- **ブロック 0 ＝ディレクトリブロック**: +0 マジック "TMEM"、
  +4 版 (1)、+6 総ブロック数 (LE16)、+16 から **8 件×16 バイト**
  のエントリ（TOSD エントリと同形式: 名前 10 バイト空白詰め／
  開始ブロック LE16／サイズ LE16／ロードアドレス LE16）。
  名前先頭バイト 0 ＝空きエントリ。
- **ブロック 1 ＝FAT ブロック**: LE16 エントリ×総ブロック数。
  0x0000 ＝空き、**0x8000｜次ブロック ＝リンク**（最上位ビットは
  第 31 話のクラス標識＝実行可能なメインメモリ側）、0xFFFF ＝
  チェーン終端（ブロック 0・1 は恒常的に 0xFFFF）。
- **操作**: MINIT（初期化／照会）、MDIR（ディレクトリ位置）、
  MSTORE（名前付き格納。ロードアドレスとして転送元アドレスを
  記録）、MFREE（解放）。**ロード＋実行は IOCS ではなくシェル層**
  の機能（N コマンドの R。TOSD の R と同層）であり、記録された
  ロードアドレスへ復元してからコールする（RET でシェルへ復帰）。
- シェルコマンド **N**: 無引数＝イメージ一覧＋空きブロック数、
  `N I [n]` ＝初期化、`N S 名前 アドレス 長さ` ＝格納、
  `N R 名前` ＝ロード＋実行、`N F 名前` ＝解放（16 進表記）。

### 2.6 RS-232C ボード（i8251、X1 のみ・コア側デバイス）

第 75 話の X1 用 RS-232C ボードの再現（xmil コア側デバイス、
EMM と同型の立場）。作中にはチップが i8251 であることしか
書かれておらず、**I/O アドレスとボーレートは作中に無い**ため、
以下は再現側の選定であり差異として明記する。本項は契約の
**追加**であり、既存の契約値の変更ではない。

- **ポート**: 0x0C00＝データレジスタ、0x0C01＝制御（書）／
  ステータス（読）。ページ 0x0C は本コアで全 ROM タイプ共通に
  空いており（0x0B＝機種によりバンクメモリ、0x0D＝EMM、
  0x0E 以降は既存デバイス群）、拡張ボードの置き場として選定
  した。ページ内の他アドレスはこの2レジスタのミラー。
- **レジスタモデル**: Intel 8251 のモード／コマンド／
  ステータス規約に従う。ステータスビットは TxRDY（保持
  バッファ空き）／RxRDY（受信 FIFO 非空かつ受信有効）／
  TxEMPTY（保持バッファ・シフトレジスタとも空）／PE・OE・FE
  （ラッチ式、OE のみ発生しうる）／DSR（ホスト接続時に 1）。
- **ボーレート**: ボードのボーレート生成器は 153,600 Hz
  固定とし、モード語の分周比が名目ボーレートを決める
  （×16＝9600 baud）。分周設定は TxRDY／TxEMPTY の時間
  振る舞い（1 フレーム＝スタート＋データ＋パリティ＋
  ストップのビット時間）にのみ効き、ホスト側の実転送は
  PTY の速度に委ねる。
- **ホスト接続**: 環境変数 `XMIL_SERIAL` が文字デバイス
  （通常は PTY のスレーブ側）を指すときだけ接続される。
  未設定時はボードは存在するが未接続（送信はスケジュール
  どおり虚空へ抜け、RxRDY は立たず DSR＝0）であり、既存の
  ヘッドレス回帰の決定論には影響しない。
- **ゲスト側ドライバ**: 初期化・送受信の基本手続きは
  開発ツリー側のドライバが担います。IOCS への組み込みは本項の範囲外。

## 3. TOSD ファイル規約

作中に TOSD のバイトレイアウト自体の記述は無い。作中にあるのは
RAMDISK の IOCS 仕様（§2.4）と、FD 対応版の呼称（OUROBO/DOS）のみ。
以下はすべて再現側の形式である。

### 3.1 ディレクトリセクタ（256 バイト、ドライブごとに 1 つ）

| オフセット | 内容 |
|---|---|
| +0..3 | マジック `"TOSD"` |
| +4 | 形式バージョン（追記式＝**0**、フリーリスト式＝**1**。現行実装は追記式でありながら 1 を書いている。判定規則は §3.6） |
| +5 | ディレクトリのブロック数（ver.0 で定義。0 は 1 とみなす＝旧形式。§3.6） |
| +6..7 | 次の空きレコード／ブロック（LE16）。初期値: FD＝48、RAMDISK＝1 |
| +8..15 | （初期化でゼロ） |
| +16.. | エントリ 15 件 × 16 バイト（+16＋15×16＝256 でセクタを使い切る） |

（注）本節の数値（ディレクトリ 1 ブロック・エントリ 15 件・RAMDISK の
次空き初期値 1）は ver.0 以前の形式の記述である。FS1（ver.0）ディスク
ではディレクトリの複数ブロック化とデータ開始位置が変わるため、
§3.6 を正とする。

### 3.2 エントリ（16 バイト）

| オフセット | 内容 |
|---|---|
| +0..9 | 名前 10 バイト（空白詰め。**先頭バイト 0x00 ＝空きエントリ**） |
| +10..11 | 開始レコード／ブロック（LE16、そのドライブ自身の番号体系） |
| +12..13 | サイズ（バイト、LE16） |
| +14..15 | ロードアドレス（LE16） |

拡張子フィールドは無い（拡張子はテープ／ブートヘッダ側のみ、§3.5）。
削除フラグ等の属性フィールドは無く、空き判定は名前先頭 0x00 のみ。

### 3.3 ドライブ別の配置

- ドライブ 0 ＝ FD: 単位は「レコード」＝256 バイト。レコード番号は
`((track*2 + side) << 4) | (sector - 1)`。レコード 0..31 ＝ブート／
システム領域（0＝IPL ヘッダセクタ、1–＝シェル本体）、32 ＝ディレクトリ
セクタ、48..1279 ＝ファイルデータ領域、最大 1280 レコード（320KB）。
33..47 は現行形式では未割当て（ver.0 では 33..39 がディレクトリ継続、
40 が空き目次、41..47 が予備。§3.6）。
- ドライブ 1 ＝ RAMDISK: 単位は「ブロック」＝256 バイト。ブロック 0 ＝
ディレクトリ、1– ＝データ。容量は RINIT の確定ブロック数。
（FS1 ではブロック 0..1 ＝ディレクトリ、2 ＝空き目次、3– ＝データ
となる。§3.6 を正とする）
- ドライブ切替はシェルの `U` コマンド（0＝FD／1＝RAMDISK）。

### 3.4 命名と割当て

- TOSD 名: **最大 10 文字**、空白詰め、**格納時は大文字化**（入力は大小
不問）。空トークンと 10 文字超はエラー。使える文字種の明示的な制限表は
（空白が区切りになること、比較が 10 バイト完全一致である
ことのみ確定）。サブディレクトリは無い（フラット、最大 15 ファイル。
FS1 では FD 127 件／RAMDISK 31 件。§3.6）。
- 割当ては**連続・追記のみ**: 必要単位数は `((len-1) >> 8) + 1` で
切り上げ、次空きポインタから連続確保してポインタを進める。
（FS1 では空き目次による first-fit の再利用が加わる。§3.6）
- 上書き時: 新データの単位数が旧サイズ以下なら旧領域を再利用（開始位置
不変）。入らなければ旧エントリを解放（名前先頭を 0）して末尾に追加
する。解放された旧領域は再利用されない（断片化の回収機構は無い）。
- 削除コマンドはシェルに無い（F／W／R／U／I のみ）。削除は上書き時の
解放としてのみ発生する。（ver.0 では削除操作と空き目次を追加する。
§3.6 を参照）
- ロードアドレスの記録: `W name addr len` は書込み開始アドレスを記録。
EDAS の保存時は ORG 先頭＝ロードアドレス。`R name` は記録された
ロードアドレスへそのまま転送する（再配置フックなし）。

### 3.5 ブート用 HuBASIC ヘッダ（32 バイト）

FD レコード 0 とテープ情報ブロック（§4.1）で共通の形式。

| オフセット | 内容 |
|---|---|
| +0x00 | ブートフラグ（0x01） |
| +0x01..0x0D | ファイル名 13 バイト（空白詰め） |
| +0x0E..0x10 | 拡張子 3 バイト（再現側は `"Sys"` 固定） |
| +0x11 | パスワード 1 バイト（無視される） |
| +0x12..0x13 | サイズ（LE16） |
| +0x14..0x15 | ロードアドレス（LE16） |
| +0x16..0x17 | 実行アドレス（LE16） |
| +0x18 | 日付 6 バイト（無視される） |
| +0x1D | ディスクオフセット 3 バイト: 下位バイト＝0、上位 2 バイト＝開始レコード番号（FD 用。テープでは未使用） |

（日付とオフセットは、継承したヘッダ文書の表記では +0x1D で 1 バイト
重なって記載されている。再現側では日付はゼロ、オフセットは FD 用の
開始レコード番号のみが使われる。）

FD ブート時、互換 IPL は T0/S0/S1（256 バイト）を 0xFE00 へ読み、
このヘッダに従い `size` バイト（セクタ単位に切り上げ）を開始レコード
からロードして実行アドレスへ跳ぶ。

### 3.6 OUROBO/DOS Filesystem ver.0（2026-11-25 採用、実装未了）

§3.1〜§3.5 の TOSD に「空き目次（空き区間のフリーリストを目次セクタに
持つ方式）」と削除操作を追加したものを、**OUROBO/DOS Filesystem
ver.0** と呼ぶ（2026-11-25 採用）。形式層（CP/M 形式＋FAT、
Hu-BASIC 形式）が揃うまでの繋ぎであり、
ver.0 の範囲は TOSD 単独形式のままである。

- 空き目次の配置: FD ＝レコード 40（ディレクトリ拡張域の直後。下記）。
RAMDISK ＝ブロック 2（同じく直後）。目次位置は固定であり、+5 からは
導出しない（+5 は判定時の検証にのみ使う、下記）。目次の読み書きは
IDXBUF（§2.2。X1／PC-8801＝0xE700、MZ 両機＝0xCB00）を介して行う。
- ディレクトリの拡張（2026-11-25 追加）: 15ファイルでは開発・
ゲーム制作の実用に足りないため、ver.0 ではディレクトリを複数ブロック
に拡張する。ブロック数はディレクトリ先頭セクタの +5 に記録する
（0 は 1 とみなす）。FD は 8 ブロック（レコード 32..39、エントリ
15＋16×7＝**127件**）、空き目次はその直後のレコード 40、データ開始は
従来どおり 48（データ領域は減らない）。RAMDISK は 2 ブロック
（ブロック 0..1、エントリ 31件）、空き目次はブロック 2、データ開始は
ブロック 3。エントリ形式（§3.2）は全ブロック共通で、先頭ブロックの
16バイトヘッダ分だけ初ブロックの件数が少ない。
- 空き目次の形式（256 バイト）: +0..3 マジック `"TOSF"`、+4 件数、
+8.. に区間エントリ（開始単位 LE16／長さ（単位） LE16）×最大 62 件
（セクタ容量まで）。区間エントリは開始単位の昇順にソートして保持し、
互いに重ならないことを不変条件とする。削除時の区間登録と隣接併合は
この不変条件を維持する。
- 形式バージョン（§3.1 の +4）は、追記式＝**0**、フリーリスト式＝**1**
とする。ただし現行実装（ver.0 以前）は追記式で 1 を書いており、どの
コードもこのバイトを判定に使っていない。そのため ver.0 での判定は
**空き目次の TOSF マジックの有無を優先**する（TOSF があればフリーリスト
式、無ければ追記式として従来どおり扱う。読取り互換）。I（初期化）は
フリーリスト式を書く（バージョン 1、+5 は媒体の正規値、+6 は媒体
末尾に固定、空き目次はデータ領域全体を単一区間として初期化）。
- 判定のガード: フリーリスト式と判定するのは、次の**全て**を満たす
場合に限る。(1) 空き目次に TOSF マジックがある。(2) ディレクトリ
+5 がその媒体の正規値である（FD＝8、RAMDISK＝2）。(3) 目次が健全
である（件数が容量 62 以内、全区間がデータ領域内（データ開始から
媒体末尾まで）にある、区間同士が重ならない）。旧 FD の
レコード 40 は初期化で消去されたことがなく、旧 RAMDISK のブロック 2
は旧データそのものでありうるため、TOSF の一致だけでゴミの目次を
信頼してはならない（実データの上書きに繋がる）。条件を満たさない
場合は追記式として読み、目次は使わない。+5 が正規値の範囲外
（0／1／媒体の正規値のいずれでもない）のディスクへは書き込まない。
- 旧ツール保護（2026-11-25 採用）: FS1 ディスクでは次空きポインタ
（+6）を**媒体末尾に固定**する。旧ツールは +6 を見て「満杯」と
判断し、書込みを拒否するか追記に失敗するが、既存データを壊さない
（読取りは通常どおり可能）。FS1 対応ツールは割当てに +6 を使わず、
空きは全て空き目次で管理する（末尾の空きも通常の区間の一つとして
登録する。ポインタ巻き戻しは行わない）。既知の危険として、旧ツール
の「より大きいサイズでの上書き」は解放→追加の順序のため、追加の
失敗時に旧ファイルが失われうる。保護は破損を防ぐもので、旧ツール
を FS1 対応に変えるものではない。この危険は受入試験で確認し、
利用者向け文書に明記する。
- 削除操作: エントリを解放（名前先頭 0）し、その区間を空き目次へ
登録する。隣接区間は併合する。目次が満杯で併合もできない場合は
エントリのみ解放するが、その旨を**利用者に見える形で警告**する
（領域は REBUILD または初期化まで回収されない。黙って漏らさない）。
削除のユーザ接口（シェル組込みコマンドかディスクプログラムか、
コマンド文字）はシェルのサイズ予算を見て実装時に確定する。
- 割当て（W）: 空き目次を first-fit で走査し、合う区間から切り出す
（残りは目次に残す）。合う区間が無ければ満杯エラーとする（+6 への
追記は行わない）。§3.4 の上書き時再利用の規則は不変。
- 目次は導出データであり、REBUILD を用意する（2026-11-25 採用）:
割当ては連続であり、各エントリが開始位置とサイズを持つため、空き
区間は「データ領域全体 − 全エントリの占有」から常に再計算できる。
空き目次はその計算結果のキャッシュと位置づける。REBUILD は目次を
エントリから再構築する操作で、削除のディスクプログラム内か、簡易
ファイルマネージャーの check／repair として置く。旧ツールの解放
リーク、目次満杯時のリーク、削除・作成途中のリセットによる不整合、
目次セクタ自体の破損は、いずれも REBUILD で回復できる。読み込み時
（または削除・割当ての前）に目次の不変条件（区間同士が重ならない、
エントリと重ならない、システム領域に入らない）を検査し、違反なら
書込みを拒否して REBUILD を促す。
- ファイルの連続性は維持する（区間は常に連続割当て）。断片化は
区間単位で発生しうるが、ファイル読みは従来どおり連続読みでよい。
- 初期化（I／dir_init）: ディレクトリの**全ブロック**を消去する
（先頭ブロックにヘッダを書き、継続ブロックはゼロで埋める。先頭
セクタだけの初期化では継続域に他形式の残存バイトが残る）。空き目次
セクタも初期化して書く（TOSF＋件数 1、区間はデータ領域全体）。+6 は
媒体末尾に固定する。
- 旧ディスクの移行: FD はレコード 33..47 が従来未使用のため、追記式
FD はその場で移行できる。初回の FS1 書込み時にディレクトリ継続
ブロックをゼロ初期化し、空き目次を「旧次空きポインタから媒体末尾
まで」の単一区間で初期化して、+5（＝8）と +4（＝1）を更新し、+6
を媒体末尾に固定する（旧ツール保護）。この時点での空きは旧次空き
ポインタ以降の末尾のみであり、既存ファイル（データはレコード 48
以降）と競合しない。RAMDISK はブロック 1..2 が旧データでありうる
ため、その場の移行は行わない。FS1 の RAMDISK は再初期化によって
のみ作る（再初期化時も +6 は媒体末尾に固定する）。
- RAMDISK の最小構成: 総ブロック数は **4 以上**（ディレクトリ 2＋
空き目次 1＋データ 1）を要する。4 未満の RINIT／初期化はエラーと
する。RDCAP 96／80／68 の機種では、overhead 3 ブロックを引いた
データ容量はそれぞれ 93／77／65 ブロックになる。

## 4. テープ形式

### 4.1 論理形式（全ターゲット共通の契約）

- テープはプログラムの列。各プログラムは**情報ブロック＋データブロック**。
- 論理情報ブロック（IOCS の TINF／TWINF で交換するバッファ）は
**32 バイト**で、レイアウトは §3.5 の HuBASIC ヘッダと同一
（名前 13 バイト空白詰め・大文字、拡張子は現行全機種 `"Sys"` 固定）。
- チェックサム: 32 バイトの**バイト和（LE16）2 バイトを +0x20 に付加**
（バッファ上は 34 バイト）。互換 IPL はこの 2 バイトを読むが検証しない。
- 論理形式のどこにもタイミング情報は無い（速度は物理層のみの差し替えで
変更可能に設計されている）。
- シェルの T コマンドは情報ブロックのロードアドレス（+0x14）へデータ
ブロックを読む。実行アドレスはシェルでは使われていない。

### 4.2 X1 物理層（CMT ビット列）

- バイト送信形式: **スタートビット "1" ＋ 8 ビット MSB ファースト**
（パリティなし、末尾ビットなし）。
- 情報ブロックのリーダ: `"1"`×800（IPL は連続 255 個以上の "1" を探索し、
その後の "1" を読み飛ばして最初の "0" まで進む）、`"0"`×40、`"1"`×41、
続いて 34 バイト（情報 32B＋チェックサム 2B）。
- データブロックのリーダ: `"1"`×800、`"0"`×20、`"1"`×21、続いて本体
N バイト（N ＝情報ブロックのサイズ）。データブロック側のチェックサム
は無い。
- `.cmt` ファイルは生のパックドビット列（MSB ファースト、1 ビット＝
1 テープビットセル、末尾は "1" でパディング）。
- **WAV 容器（相互運用形式、2026-11-24 追加）**: テープイメージの
相互運用の正規形式は WAV とする。コア（xmil `io/cmt.c`）は
`XMIL_TAPE` の拡張子で区別し、`.wav` なら PCM WAV を読み書きする。
  - コアが読む形式：RIFF/WAVE、PCM（format 1）、8 ビット
  （unsigned）／16 ビット（signed LE）、モノ／ステレオ（ch 0 を
  使用）、任意のサンプルレート。デジタイズは **固定しきい値**
  （サンプル範囲の中点：16 ビットは 0、8 ビットは 128）のみ。
  ビットへの復号はレコーダと同じ規則（セルは立上りで始まり、
  ビットは現行速度のサンプル点＝§4.4 の判定点におけるレベル）。
  再生タイミングはコアのタイミング表で再合成される。
  - **正規 WAV**（コアの録音形式であり、相互運用の正）：
  48000Hz、16 ビット signed、モノ、矩形波 ±12000、位相は
  §4.4 のタイミング表どおり、位相サンプル数は累積剰余
  繰り越しで決定する。
  - 汚れた WAV（DC オフセット・レベル変動・極性反転・
  ノイズ）の処理はコアの責務ではない。ホスト側ツール
  `wavclean`（`tools/wavclean.py`）が正規化して
  正規 WAV を出す。`.cmt`⇔WAV 変換も同ツール経由。
  - 論理形式（§4.1）は不変。WAV は物理層の容器の追加であり、
  `.cmt` は回帰用に残る。

### 4.3 MZ 物理層（標準 MZ 形式）

- 情報ブロックは標準 **128 バイト MZ ヘッダ**として送られる: +0 属性、
名前 17 バイト（CR 0x0D 詰め）、サイズ／ロード／実行は論理形式と
同じ +0x12 系オフセット、残りはゼロ。ヘッダは **2 回送り、両コピーを
検証・相互照合**する。コピー間は `"0"`×256 のギャップ＋追加の `"1"`。
- マーク形式: 無音区間の後、ロングマーク＝`"0"`×10000、ショートマークは
ヘッダ用 40/40/1、データ用 20/20/1。
- バイト送信形式: **スタート "1" ＋ 8 ビット MSB ファースト ＋ 末尾 "1"**
（X1 との差異は末尾ビット）。
- データブロックのチェックサムは**ポップカウント**（全データの 1 ビット
数の合計、2 バイト BE）。情報ブロックのバイト和（LE）とは別規約。
- 物理層そのものに直接の互換は無く（X1＝ビット列.cmt、MZ＝PWM 音声）、
「統一」とは論理内容の統一を指す。相互読取りは変換ツール経由の
再レンダリングで実証済み。

### 4.4 ビットタイミング

- クラシック（X1）: 全ビットセルは立上りで始まり、立上り後
**約 185µs** のレベルで判定（High＝"1"、Low＝"0"）。書込波形は
"1"＝High 約 380µs＋Low 約 280µs（セル約 660µs）、"0"＝High 約 100µs
＋Low 約 280µs（セル約 380µs）。実効測定（リーダ含むワイヤ時間換算）
＝1,738 bps。公称 bps の明記は資料に無い（作中では標準＝1200bps が前提）。
- クラシック（MZ）: 読取りはマーク較正方式（§4.5）のため単一の
公称値に依存しない。書込実測（48kHz WAV サンプル数）は 80K:
"0"＝26–27／"1"＝57–58、80B: "0"＝27–28／"1"＝53–54。
- **許容範囲（公差）の数値はクラシック／4800 とも定めが無い。**
実測値と較正方式のみが存在する（§8）。
- 4800bps 変種: 作中では第 19 話で 4800bps を改造 IOCS の
標準速度／フォーマットと確定（方式は H/L 独立変調、X1／MZ-80B は
オプションで 9600bps）。**再現側の変調方式は作中方式ではない**
（到達点＝標準の 4 倍・3 機種共通標準フォーマットのみ作中に合わせた）。
- X1 再現値: "1"＝High 130µs＋Low 70µs（セル 200µs）、"0"＝High 35µs
＋Low 130µs（セル 165µs）。リーダは立下り同期→立上り待ち→約 +65µs
遅延後に 1 回サンプル。実効 5,279 bps。コア側は環境変数
`XMIL_TAPE_BPS=4800` でタイミング表を切替える。
- MZ 再現値: 書込はビルド時バリアント（`TAPE4800` 定義）で位相定数を
原則 1/4 周期化。実効は 80B＝4,185 bps（読み書き達成）、80K＝3,812 bps
（**書込のみ達成、読込は未達**＝2MHz での較正閾値の漂いにより
ヘッダチェックサムが一度も通らなかった。制約として記録）。
- **X1 IPL の CMT ブートはクラシック速度のまま**（互換 IPL ROM は
第三者成果物で変更しない）。4800 の主経路は FDD 起動後の IOCS テープ。
- 9600bps（作中のオプション）は再現では対象外・未検証。

### 4.5 リーダの較正方式（MZ、クラシック／4800 共通）

固定閾値を廃し、各セクション頭のロングマークの中で較正する: 相互に近い
周期を 24 個集め（実行中最大値の 1.5 倍超は二重周期として読み飛ばす）、
ソートして 75 パーセンタイル×1.5 を閾値とする。分類は周期／High 幅／
周期+High の合計のいずれかが閾値超で "1"。安全弁として、マークの
High 幅の百分位が 2 以下かつ周期の百分位が 8 以上の場合に限り
High／合計の軸を無効化する。これにより 1 つのリーダがクラシック・
4800 両方のテープをモード切替なしで読む。IPL 側も同じ方式。
X1 側は較正方式ではなく固定遅延＋単一サンプルである。

## 5. TOSR リロケータブル形式 v1

形式名 TOSR（TapeOS Relocatable）は再現側の確定名であり、作中名称では
ない。再配置の骨格（256 バイトブロック単位、上位 8 ビットのみ書換え、
再配置情報は実行バイナリの後ろに添付）には典拠がある（第 22 話、
導入順序は第 26 話）。符号化方式以下の具体は。

### 5.1 ファイルレイアウト

```
+0 本体（ページ整列でアセンブルされた機械語）
+body_size 再配置ビットマップ（ceil(body_size/8) バイト）
+... 外部参照部（v1 ではサイズ 0 固定）
+total-16 トレーラ（16 バイト固定）
```

- モジュールの原点（ORG）は**256 バイト境界（ページ整列）が必須**。
ページ境界でないモジュールは TOSR 化できない（アセンブラがエラー）。
- デルタ＝ロードページ − 原点ページ。**符号付きページ差 −128〜+127** の
範囲内だけが対象で、範囲外配置は拒否される。ページ倍数の加算は下位
バイトに影響しないため、印付きワードの上位バイトへの加算のみで
厳密に正しい。
- 本体サイズの形式上の上限は 64KB。実用上限は機種の OUTMAX（§2.3）。

### 5.2 再配置ビットマップ

- 本体 1 バイトにつき 1 ビット（本体の 12.5% 固定費）。本体オフセット
`o` のビットは、ビットマップバイト `(o div 8)` のビット
`(7 - (o mod 8))`（**MSB-first**。Z80 の `sla` 系でキャリー判定でき
パッチループが最小になるため）。
- ビットが立つのは、生成側が「モジュール内アドレス由来の値」として
出力した 16 ビットワードの**上位バイトのオフセット位置のみ**。
下位バイトには印を付けない。IOCS テーブルアドレス・署名セル等の
**絶対定数には印を付けない**（生成側の責任）。相対分岐（JR/DJNZ）や
IX/IY 変位は元々位置非依存のため対象外。
- 生成側の印付け規則（EDAS）: 値そのものではなく値の由来（原点係数）で
決める。ラベルと `$` は係数 1、数値・文字定数・数値 EQU は 0。加算は
XOR、減算は「左 AND NOT 右」、単項マイナスは 0。マークは `emit16` の
一点に集約される。NEWASM はフィックスアップリスト方式だが、出力形式
と属性代数は EDAS と同一。

### 5.3 トレーラ（16 バイト固定、全て LE）

| オフセット | サイズ | 内容 |
|---|---|---|
| +0..1 | 2 | マジック `"TR"` |
| +2 | 1 | 形式バージョン（**1**） |
| +3 | 1 | フラグ（§5.4） |
| +4 | 1 | 原点ページ（原点アドレス >> 8） |
| +5..6 | 2 | 入口オフセット（本体先頭からのバイト数） |
| +7 | 1 | ヒープ要求ブロック数（256 バイト単位、0＝ヒープなし） |
| +8..9 | 2 | 本体サイズ |
| +10..11 | 2 | ビットマップサイズ |
| +12..13 | 2 | 外部参照部サイズ（v1 は 0） |
| +14..15 | 2 | チェックサム |

- チェックサムは、チェックサム欄より前の全バイト（本体＋ビットマップ＋
外部参照部＋トレーラ先頭 14 バイト）の**単純バイト和（mod 65536）**。
- 検証規則: ローダ／スタブはマジックとチェックサムと
「本体＋ビットマップ＋外部＋16 ＝ファイルサイズ」を検証し、失敗したら
TOSR として扱わない。ビットマップサイズは本体サイズから導出できる
ため冗長だが、検証の単純さを優先して明示する。
- 入口オフセット: 自己再配置可能な実行ファイルでは**スタブ長（109）を
入れる**（入口＝スタブ直後＝ユーザーコード先頭）のが v1 確定。
EDAS／NEWASM の出力では常にこの値で、ソース側で入口を選ぶ手段は
v1 には無い（形式上は任意値を取れる）。
- ヒープ要求: EDAS／NEWASM では `RELOC [式]` の任意オペランド（0〜255、
既定 0）。v1 の既定配置は「本体＋情報部の直後をページ整列して
ヒープとする」。なおヒープを消費する側（ローダ）はまだ存在しない。

### 5.4 フラグ（トレーラ +3）

- bit0: 外部参照部あり／bit1: 自己再配置スタブ付き／bit2: 入口オフセット
有効／bit3: ヒープは本体直後（ページ整列）。bit4..7 は。
- 実際に使われる値: 自己再配置可能な実行ファイルは **0x06**（bit1＋bit2）。
EDAS／NEWASM の TOSR 出力は常に 0x06 で、ヒープ指定の有無では変わらない。

### 5.5 外部参照部

- v1 では**サイズ 0 固定**。単一モジュールの再配置のみが対象で、
外部シンボルは持たない。サイズ欄だけが確保済みであり、v1 ローダは
「外部参照部あり＝未対応として拒否」と安全に振る舞える。
- v2 素案（v1 仕様ではない）: エントリ列＝｛名前 12 バイト、パッチ位置
オフセット（LE16）、加算定数（LE16）｝、結合はリンク専用ツールが行う。

### 5.6 自己再配置スタブ

- 大きさは **109 バイト**（実測。うちパッチ手続き自体は約 30 バイトで、
大半は自己配置の検出）。EDAS／NEWASM はこのテンプレートを逐語的に
内蔵する。計画段階の「16 バイト級」という見積もりは下記の方式変更で
訂正された。
- 検出方式は**マーカ走査**:
計画当初の `CALL $+3`／`POP HL` は Z80 では成立しない（CALL の
オペランドは絶対アドレスであり、転送先では原点側へ跳んでしまう。
シェルの G もレジスタ／スタック経由で自分のアドレスを知る手がかりを
与えない）。そこで候補ページ（0x00〜0xFF）ごとに、そのページを像の
先頭と仮定して末尾位置のトレーラを検査し、マジック `"TR"` と形式
バージョンが一致したら全体のバイト和を格納チェックサムと比較する。
一致した候補が自分の像である。デルタ 0 なら何も書き換えず入口へ
落ちる。デルタ非 0 ならビットマップを MSB 側から消費しながら本体を
走査し、マーク付き上位バイトにデルタを加算してから入口へ落ちる。
- **自己再配置は冪等でない**: 一度パッチした本体を再び別
アドレスへ転送して実行するとデルタが二重に効く。**パッチ済み本体の
再転送は禁止。再利用時は必ずファイルから読み直す。**
「再配置済み」ビットを立てる案は要否がで、v1 のフラグ割当て
には含まれていない。
- **全体サイズの下限**: 自己再配置可能な完成像は **256 バイトを超え
なければならない**（違反はエラー "TOSR IMAGE TOO SMALL"）。根拠は
シェルの `R` が最終部分セクタを DIRBUF（0xE500、ページ境界）経由で
配置するため、像が 256 バイト以下だとロード直後に DIRBUF に像全体の
コピーが残り、マーカ走査が誤認する恐れがあること。これは自己再配置
固有の制約であり形式自体の制約ではない。
- 生成側エラーの文言（EDAS／NEWASM 共通）: 原点がページ整列でない
"TOSR ORG NOT PAGE ALIGNED"、像の末端が OUTMAX 超え "TOSR IMAGE TOO
BIG"、`RELOC` がソース先頭でない "RELOC MUST HEAD SOURCE"。
ORG を書かない場合の既定原点は 0x8000。
- TOSD との関係: TOSD ディレクトリ形式は変更しない（バージョン 1 の
まま）。TOSR ファイルのロードアドレス欄には**原点アドレス**を記録する
（番兵値を書く案は、旧シェルが暴走アドレスへ読み込む危険があるため
不採用）。旧シェルの R＋G でも、原点配置＋スタブ付きなら動作する。
TOSR でないファイルは従来どおり絶対形式として処理する（判定は
トレーラのマジック＋チェックサム）。
- テープ経由の TOSR 標識（拡張 3 バイトの先頭を 'R' に変える案と、
原点読み＋メモリ内転送方式のどちらにするか）は。

| PC-8801 GVRAM トランポリンスタブ | **160 バイト以下** | 0xBF00 に置き KIMG 0xBFA0 の下に収める | 実測は（ゲート条件のみ） |
| TOSR 本体サイズ | 形式上 64KB | §5.1（実用上限は OUTMAX） | — |

## 7. 契約チェックとの対応

`tools/contract-check.sh`（基準値 `tools/contract-manifest.txt`）が
機械検証する範囲:

| チェック | 内容 | 主な対応節 |
|---|---|---|
| HASH（179 件） | 非モニタ成果物バイナリの sha256 バイト同一性。対象は監査で照合されたバイナリ集合から揮発性の RAM ダンプと正規モニタビルドを除いたもの＋デバッグスタブ成果物 | 全体 |
| IOCS（5 件） | 正規モニタビルド 5 種（X1／MZ-80B／MZ-80K／PC-8801／X1 4800 版）のバイナリ内 `iocs_template` のバイト同一性と JP パターン（84 バイト。X1 系 2 種は 31 エントリ＝93 バイト、マニフェスト行の第 5 フィールドに長さを記録） | §1.1 |
| EQU（58 件） | `common.inc` のエントリ番号 26 件と、各 `machine_*.inc` の IOCS_BASE／LOADADDR／STACKTOP／SIGADDR／RDMAX／RDBASE／RDSEG1／RDBASE2／RDCAP | §1.1、§2.1、§2.4 |
| TEXT（3 件） | EDAS／NEWASM／SCED の各ソースに `org 04000h` が残ること | §2.3 |
| SIZE（16 件） | §6 の上限のうちファイルサイズで判定できるもの | §6 |

モニタ／シェル本体そのものはバイト同一性の対象にしない（機能追加で
正当に変化するため）。代わりに IOCS テンプレート領域の同一性で
「接口が変わっていないこと」を検証する。正当なインターフェース変更が
入る場合は、本仕様を更新し、関係スイートを再実行した上で
`sh tools/contract-check.sh --generate` で HASH／IOCS の基準ハッシュを
再生成する（手順の詳細はスクリプト冒頭コメント）。

### 7.1 変更の分類と承認ゲート

インターフェース変更とベースライン再生成には、次の 3 分類を
適用する（2026-11-25 採用）。

- 分類 A「追加」： 既存の値・アドレス・形式を一切変えず、追加
  のみを行う変更。実装者の判断で進めてよく、記録のみを要する。
- 分類 B「観測可能な変化」： 互換ではあるが既存の振る舞いが
  変わる変更、または未定義だった点が定義される変更。再生成の
  前に影響範囲（影響を受けるバイナリ・ディスク・上層）を列挙
  し、ユーザーへ事前に連絡するか、定例報告に含める。
- 分類 C「破壊的」： 既存のアドレス・形式・慣行を変更し、既存
  バイナリ／ディスクの再作成や変換を要する変更。ユーザーの
  事前承認が必須であり、影響範囲と移行手段を添えて承認を得て
  から着手する。

機械的支援として、`--generate` の差分に EQU／IOCS の値変更、
または既存 HASH 行の変更・削除が含まれる場合、その再生成は
分類 B 以上として扱う。分類（`--class B|C`）と承認者
（`--approver`）の指定が無ければ、`contract-check.sh` は
再生成を拒否する。通過した再生成は `tools/contract-changes.md`
に日時・分類・承認者・メモを追記して記録する。新規エントリの
追加は、ハッシュ欄を 0 埋めにした行を足してから再生成する形
とし、純粋な追加のみの差分は分類の指定なしで通る。

（注）本リポジトリに同梱する `tools/contract-manifest.txt` は、
上表のうち公開範囲（X1）に属する項目を抜粋し、パスをリポジトリ内の
配置に読み替えたものです。全機種を対象とする完全なチェックは、
開発ツリー側で同じ形式のマニフェストにより実施しています。

検証範囲外（監査＝全回帰スイートの一括実行でのみ確認されるもの）:
エミュレータ上での実際の動作、画面表示、タイミングの実測再現、
TOSR の転送先での実行、テープの相互読取り等。

## 8. 仕様に書き切れていない既知の依存・未決事項

監査で問題が検出されたのに契約チェックで検出できなかった場合は、
ここへ項目を追加し、可能なものから §1–§6 と契約チェックへ還元する。

1. **スタック消費量**: 全 IOCS エントリについて数値規定が無い（§1.2）。
上層が深い呼出しを行う場合の余裕は実装依存のままである。
2. **AF／フラグの保存**: キャリの意味論（エラー表示、未実装スタブ）を
除き未規定。HEXOUT の A の戻り状態も未規定。
3. **ワークエリアの直接参照**: §2.2 のワークはモニタ内部配置であり
上層向け保証ではないが、検証ハーネスは SIGADDR／LASTCMD 等に依存し、
PC88 では `cur_attr` の直接書換えの慣行がある。アドレスはビルド
（機種・構成）依存であり、保証として固定はされていない。
4. **ファイル層の重複実装**: TOSD の名前付きファイル処理は IOCS の外で、
シェル／EDAS／NEWASM／SCED が各自に同形式を実装している。形式の
一致は各スイートの往復検証に依存しており、IOCS にファイル層エントリ
を新設して一本化するのは将来の候補として残る。
5. **PC-8801 の FD エラー意味論**: 下位プロトコルが状態バイトを返さない
ため、DREAD／DWRITE は転送完了時に常にキャリクリアとなり、失敗を
この層では判別できない（他機種は実エラーでキャリセット）。
6. **テープタイミングの公差**: クラシック／4800 とも許容範囲の数値は
未規定。実測値と MZ の較正方式のみが存在し、書込波形がどこまで
ずれても読めるかは仕様化されていない。MZ-80K の 4800 読込は未達
（制約として記録済み）。
7. **MZ 両機モニタのサイズ上限**: 未規定。80B は MZT 直接ロード、
80K は IPL.ROM テープロードであり、X1 式の 7,936 バイト上限は
適用されない形のままである。
8. **サイズ上限の不揃い**: NEWASM／SCED の 10,240 バイトと EDAS の
9,216 バイト（0x6400）の差の理由は資料に記載が無い。
9. **TOSR の未決事項**: フラグ bit4..7 の割当て、「再配置済み」ビットの
要否、テープ経由の TOSR 標識方式。汎用ローダは
未実装であり、ヒープ要求を消費する側は存在しない。
10. **TOSD の未定義領域**: ディレクトリセクタ +5 と +8..15、FD レコード
33..47 の用途。断片化の回収機構は無く、ファイル名に使える文字種の
明示的な制限表も無い。
11. **X1 EMM の未割当て領域**: 0x1C000 以降の TapeOS／SCED による
割当ては未定義。
12. **作中後期仕様は範囲外**: 第 27 話の大容量 RAMDISK（320KB・FAT16・
サブディレクトリ 1 段）や第 97 話の OUROBO/ROS 実行形式は未実装で、
本仕様の TOSD／RAMDISK 形式とは対応付けられていない。
13. **EDAS の既知の不具合（現行の観測可能な振る舞いとして凍結）**:
(1) EQU 式のシンボル参照が壊れている、(2) IM 命令の第 2 バイトが
不定値になる（再現では全て ED 20 になった）。いずれも開発資料に
記録された潜在バグで、修正する場合はインターフェース変更として
扱う。EDAS と NEWASM の命令形式差異（`LD (nn),HL` の ED 63 形式は
EDAS のみ、RLD/RRD とブロック IN/OUT は NEWASM のみ）も同様に
現行の差異として記録する。
14. **shell4800 のヘルプ表示**: TAPE4800 変種のヘルプに、その変種では
存在しない X コマンド（デバッグスタブ）の行が表示される既知の
化粧的差異がある（`data_x1.inc` のヘルプ文字列が DBGSTUB で
ゲートされていないため。表示のみで機能への影響はない。
開発資料に記録済み）。
15. **数値の出典間差異**: スタブ導入前の X1 シェル実測が、資料により
5,181 バイトと 5,182 バイトで 1 バイト異なる。理由は資料に記載が無い。
16. **メインメモリプール（§2.5）の制約と未決事項**: 同時イメージ数
8 件・プール 64 ブロックは固定上限（拡張は MINIT の再初期化を
伴う再設計事項）。プールは揮発性で、電源断／リセットで内容は
失われる。作中との差異: (1) 作中の GRAM 側プールは再現側 X1 の
GRAM がセルアドレス方式で線形ストアに使えないため設けていない
（作中の前提は HuBASIC 的 GRAM）。(2) 作中の FAT16 は第 27 話の
RAMDISK 側仕様が典拠だが、再現側の RAMDISK は TOSD のままで
あり（§8-12）、FAT 方式は本プールが初導入である。(3) MSTORE の
同名はエラーであり TOSD の W（置換）とは意味論が異なる——
失敗した格納で旧イメージを失わないための意図的な差異。
(4) 移動に伴う再配置書換え（第 31 話）とマルチタスク実験
（第 32 話）は後続項目であり、本プールはアドレス固定の
イメージのみを扱う。
17. **プリンタデバイス接口は暫定**（2026-11-25 決定）: ゲスト側
プリンタドライバのデバイス接口は暫定仕様として本節に置く。確定は
その実装と検証を経てからとし、それまでは変更を区分 B として扱う。
18. **言語側ファイル層は FD のみ**（2026-11-25 確認・明記）:
TinyBASIC／SmallC のファイル層（tbcore／sccore）は FD（ドライブ 0）
専用であり、RAMDISK 上のファイルは言語側からは見えない。SCMCORE
の自動ロード（言語ライブラリ id 22）も FD のディレクトリしか
探さないため、RAMDISK に置いた SCMCORE は自動ロードされない
（不在時と同じく SCMERR 0xFB になる）。シェル側の媒体切替（U
コマンド）とは独立の制限である。解消は FS1（§3.6）の媒体別
ディレクトリ扱いを前提に、媒体探索順 RAMDISK＞FD＞CMT（2026-11-25
の原則）で別途行う。

## 9. 移植可能プロファイル（portable profile）

（定義の確定は
MZ-2000／700 移植の調査で行う予定。）

TOS の契約（§1 IOCS コールテーブル＋§3 TOSD）の部分集合として、
全機種で保証される最低共通の能力範囲を「移植可能プロファイル」
と呼ぶ。アプリケーションがこのプロファイルの範囲内でのみ
書かれていれば、TOS の載ったどの機種でも動作することが期待
できる。プロファイルの骨子（暫定）:

- 表示: テキストのみ。色は 8 色まで（デジタルパレット範囲）。
  グラフィック描画・PCG・アナログパレットには依存しない。
- 音: BEEP（IOCS エントリ）のみ。PSG／FM 音源には依存しない。
- 入力・ファイル: IOCS のコンソール入出力と TOSD の範囲内。

プロファイルを超える能力（グラフィック、アナログ階調、
音源等）を使う場合は、能力問い合わせ（グラフィックドライバの
能力表 API）で確認し、無い環境では
プロファイル範囲へ格落ちさせる二段構えを原則とする。

背景: 互換レイヤ群（S-OS 互換レイヤ、CP/M ラッパー、
Hu-BASIC 形式互換層）は TOS の契約の上に載るため、TOS の
移植に原則として追随する。追随を妨げるのはメモリマップ差
（§2、IOCS テーブル配置等）、能力差（本節）、ハードウェア
病理（例: MZ-80K の 4800bps テープ読み未達）の 3 種であり、
移植調査ではこの 3 点の洗い出しを先行させる。

## 10. 機種情報・機種判定 API（決定事項、未実装）

（2026-11-24 決定。S-OS の教訓による：S-OS の機種
コードはバイナリに埋め込まれた静的な名札であり、起動時に
実ハードとの照合は行われなかった——MZ-2500 が MZ-2000 版
（コード 11h）を 2000 モードで使用していた事実がその証左。
OUROBO／ROS／DOS／TOS ではこの欠点を学習し、以下の 2 つの
API を持つ。実装は今後の課題（未着手）。
IOCS エントリの追加を伴う場合は正当な契約変更として扱い、
ベースライン再生成の内訳を記録する。）

### 10.1 機種情報を返す API

ビルド時に埋め込まれた機種情報を返す。返す内容の候補：

- 機種コード（TOS 独自の採番表による。X1／MZ-80B／MZ-80K／
  PC-8801／MZ-2000／MZ-700 等、ビルド対象機種ごとに一意）
- TOS の世代・バージョン
- 能力サマリ（§9 の能力問い合わせと整合させる。詳細な能力表は
  グラフィックドライバの領分とし、ここでは要約に留める）

### 10.2 機種判定 API（可能なら）

実行時にハードを能動的に調べて判定する。現実的な範囲：

- **ファミリ内のバリエーション判定**：同一ビルドが複数の
  バリエーションをカバーする場合の切り分け（GRAM 有無、
  X1 と X1turbo の区別等）
- **付属ハードの検出**：CTC・アナログパレット・EMM 等の有無
  （能力検出と同じ「書いて読み戻す」方式を踏襲する）
- **ビルド対象との不一致検出**：想定外の環境で起動したことを
  検出して報告する（S-OS に無かった照合の、可能な範囲での実装）

判定できない環境・項目については「不明」を正直に返すこと。
推測で機種を名乗らない。

能力問い合わせは一般に **3 値（有／無／不明）** を返す（2026-11-25
決定）。「不明」を「無」に丸めない。
この規則はグラフィックドライバの能力表 API と本節の API で共用し、
適応診断プログラムもこれを使う。機種情報・機種判定 API の実装は
2 段構えとする：最小版（機種コードと基本能力）を FDD 互換対応より
前に、本格版（能動判定の拡充）をグラフィックドライバの後に置く。
