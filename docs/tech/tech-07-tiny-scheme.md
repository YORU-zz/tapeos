# 技術解説07：Tiny Scheme

## 役割と設計

Tiny Scheme は、TapeOS 世代の環境に載せた小さな Scheme 処理系です。形態は2つあります。テープ先頭に置く単体版（第1段ローダー TSLOAD が Scheme を内蔵し、続くスクリプトを評価して環境自身を育てる）と、他の言語から埋め込んで使う組み込み版コア SCMCORE です。

設計の核は「小さなコアを Scheme 自身で拡張する」ことです。第1段は Z80 アセンブラの固定コアで、ブート時に固定長スクリプトブロックを検証して評価します。第2段スクリプトがセレクタ／シェルの役割を担い、Scheme だけでも動く環境を構成します。危険で重い操作（バイト列の切り貼りなど）はネイティブ primitive に寄せ、方針は Scheme 側に置く、という分担です。

もう一つの設計判断は、コアの単一ソース化です。組み込み版 SCMCORE は、単体版 TSLOAD のソースからコア部（`tscore.inc`）を切り出して共有し、生成ツールが変種を組み立てます。リファクタ後も TSLOAD がバイト同一であることを検証済みで、2形態が静かに乖離しないための構成です。

## 実装の要点

- TSLOAD：ロード／実行 0x2000、全体 12,255 バイトです。IPL からクラシック速度でそのまま読める形式で、直後に固定長スクリプトブロック（ファイル名 "SCRIPT"、ペイロード 4096 バイト）、その後ろに通常のロード可能ファイルが並びます
- スクリプトブロック形式：マジック "TS"、バージョン、実長、チェックサム（本文のバイト和）を持ち、ローダーは評価前に必ず検証します。失敗した場合は組み込みの素メニューへフォールバックします。固定長なので、スクリプトを書き換えても後続ファイルのテープ上の位置は動きません
- 値表現：奇数＝fixnum（15ビット符号付き、-16384..16383）、nil＝0、#f＝2、#t＝4 です。cons は4バイトセル（アリーナ 0x6000〜0x7FFF）、オブジェクトは8バイト（0x8000〜0x8FFF）、文字列アリーナは 0x9000〜0x9FFF です
- GC はありません（バンプ確保のみ、リセットはブート時のみ）。アリーナはプログラム実行全体での予算で、使い切ると E_HEAP になります
- primitive は66個です。リスト操作、述語、数値、文字列、入出力、eval のほか、テープ／スクリプト操作、ブロック編集（block-ref、block-set!、block-splice! など）、peek／poke、`(random n)`（xorshift16、種はキー待ち時間の揺らぎ）、`(date)`／`(time)`（IOCS RTGET の席をガード付きで叩き、取得できない場合は #f）、機械語ブリッジ `(call)` を備えます
- ブロック操作をネイティブ化した理由：スクリプト本文バッファ（0xA008 付近）のアドレスは fixnum で表現できず、かつ4KB ブロックへの1バイト単位の Scheme ループは無 GC のアリーナを使い切るためです
- スクリプト保存：その場上書きではなく、テープ全体の再生成です。使用している xmil コアのレコーダがテープの途中だけを上書きできないためで、全ファイルを RAM へステージングしてから1回の連鎖 REC で記録し直します。対象は後方ファイル合計12KB までのテープです
- 第2段スクリプト（stage2.scm、3,267バイト）：Scheme 自身で書かれ、プロンプト「TS> 」と ls／run／msg／save／ed（行エディタ）／menu／quit を備えます
- SCMCORE：TOSD ファイルとして置く 9,200 バイトのコアで、0x9000 に配置されます。primitive は66個から48個へ減らしています（対話面とテープ／メニューの機械はホストプログラムと競合するため外し、外した名前は未束縛として正直にエラーを返します）。cons アリーナは384セルなど、単体版より小さいのはホストと共存するためのダイエットです
- 言語との境界：SCMCORE の先頭にゲートヘッダ（マジック "SC"、版数、エラーバイト、初期化／評価／呼出の JP）を固定し、TinyBASIC の `seval`／`scall` と SmallC の `scmeval`／`scmcall` がこの規約で呼びます。評価はゲート専用のプライベートスタック（0xC400〜0xC800）で実行し、定義はプログラム実行中ずっと保持されます。整数の受け渡しは fixnum 範囲のみで、範囲外は E_RANGE、整数化できない結果は E_RESULT として報告し、黙って丸めません
- `(call)` の到達範囲：`(call)` はアドレスを fixnum で受け取るため、正数では 0x0000〜0x3FFF、負数では 0xC000〜0xFFFF しか届かず、0x4000〜0xBFFF は死域です（ロードマップ26の実装で実証された制約で、機械語ヘルパ RHIO の配置先 0xD000 はこの制約から決まりました）

## 原作との技術的差異

- 作中の拡張 Scheme との関係：作中の系譜は、院生さんが SICP 学習の副産物として書いた C 実装の TinyScheme（16ビットポインタ前提）を原形とし、32ビットセル化、ヒープの大規模拡張、マルチスレッド GC などを施して表計算を載せる、後期・大規模側の話です（第144・145話）。本実装は TapeOS 世代の Z80 ネイティブなアセンブラ製コア（GC 無し）で、規模も時代も異なる別物です（tiny-scheme.md「作中との差異」が正本です）
- 値表現の近似：作中でも、オリジナルの TinyScheme（14ビットポインタ＋2ビットタグ）が Z80 の 64KB に収まることは明示されています（第152話）。本実装の値表現（奇数タグの fixnum、タグ付きポインタ）は、その系譜と無関係に決めたものではなく、同じ制約条件から自然に似た形になったものです
- スクリプトブロックによるブート手順の自己進化、`(random)`、`(date)`／`(time)`、`(call)` は、いずれも作中に直接の対応物を持たない再現側の追加です。乱数と日付／時刻はユーザー決定（2026-11-24）による基盤部品の追加で、将来のゲーム／ツール類と常駐版 Tiny Scheme 構想の土台を意識したものです
- スクリプト保存方式：当初案の「その場上書き」から「テープ全体の再生成」へ変更したのは、エミュレータ（xmil コア）のレコーダ仕様によるもので、作中側の事情ではありません

## 数値まとめ

- TSLOAD：12,255バイト（ロード／実行 0x2000）
- 第2段スクリプト：3,267バイト（上限 4,088バイト）、スクリプトブロックは 4,096 バイト固定
- SCMCORE：9,200バイト（配置 0x9000〜0xB3F8）、primitive 48個（単体版は66個）
- 値：fixnum は -16384..16383（15ビット符号付き）
- 単体版アリーナ：cons 0x6000〜0x7FFF、オブジェクト 0x8000〜0x8FFF、文字列 0x9000〜0x9FFF
- スクリプト保存の対象：後方ファイル合計 12KB までのテープ
- 乱数：xorshift16（周期 65,535）
